# Acceptance performance record — 2026-10-21

Baseline: dev `68c4a3cc69432e07250ec4441e649cc2f2beaf66`. Comparison: the integrated fixes on `feature/complete-remaining-issues`. Both browser builds use the same installed dependency lock, Node 24.15.0, Vite 6.4.3, Windows host and Chrome 155.0.8059.85. This is a retrospective baseline comparison, not a claim that every optimization was preceded by a recorded profile.

## Browser measurements

Reproduction: archive the baseline frontend into a temporary directory, reuse installed dependencies, build with Vite, and serve baseline/current production builds on separate localhost ports. If the snapshot is inside node_modules, add `@source "../";` to its copied `src/styles/global.css` so Tailwind explicitly scans that copied frontend. Do not edit the baseline component logic. Run `PLAYWRIGHT_CHANNEL=chrome node scripts/measure-browser.mjs BASE_URL OUTPUT_JSON` sequentially for each build. The script uses mocked IPC, 60 real key inputs at 20 ms spacing, a 10,000-line source document and 500 Writing paragraphs. Source seeding is programmatic; the measured keystrokes are browser keyboard events. The input sample ends after document-level delegated handlers. Idle serialization is excluded; next-animation-frame samples include browser scheduling but do not measure GPU presentation.

Raw results: [before](browser-before.json), [after](browser-after.json).

| Probe | Before | After |
| --- | ---: | ---: |
| Initial JavaScript entry (raw / gzip, kB) | 763.78 / 219.14 | 305.05 / 83.06 |
| First New Document action available (ms) | 174.5 | 210.1 |
| Four reload probes (ms) | 48.0, 51.9, 86.7, 39.3 | 60.0, 54.4, 54.2, 68.4 |
| Source input handler p95 (ms) | 54.0 | 20.7 |
| Source next-animation-frame p95 (ms) | 145.3 | 27.6 |
| Writing input handler p95 (ms) | 4.7 | 4.9 |
| Writing next-animation-frame p95 (ms) | 17.0 | 16.8 |

The entry is smaller and source rendering improves, but startup is not proven faster: the first probe regressed in this sample and reload values overlap. Writing input is effectively unchanged within host variability; correctness/history and removal of redundant serialization are covered independently by real Milkdown tests. The 10,000-line source sample still exceeds the 16 ms target at p95; do not claim universal 60 FPS. Native textarea layout, host load and different font defaults remain contributors. The virtual gutter bounds mounted rows to the viewport plus overscan, and tests retain DOM identity when line count is unchanged. Follow-up profiling can use this same benchmark if larger-document input remains a product priority.

Editor, source view, settings, search and updater have lazy boundaries with loading/error recovery. Mermaid, KaTeX and export font data are loaded only on demand. Their large optional chunks remain part of total distribution size. Initial script requests in the raw records confirm they are absent from the welcome screen. Chunk size alone is not a latency verdict. These browser probes do not measure native Tauri process cold start or mobile hardware.

## Rust release measurements

`cargo test --release --manifest-path src-tauri/Cargo.toml test_highlight_performance_reuse -- --ignored --nocapture`

100 identical small Rust blocks with per-call syntax registry construction: **457.8232 ms**. The same workload with the immutable cached registry: **5.4646 ms**. Concurrent requests and output classes are covered by ordinary Rust tests. These are release timings, not debug results or evidence of a keystroke budget.

`cargo test --release --manifest-path src-tauri/Cargo.toml worker_responsiveness_measurement -- --ignored --nocapture`

Eight renders of a 2,000-heading sample on a single-thread Tokio executor:

| Execution | Total render time | Observed 1 ms heartbeat |
| --- | ---: | ---: |
| Synchronous parser on executor | 9.8610 s | 9.8610 s |
| Blocking worker offload | 13.1291 s | 8.3895 ms |

Offloading preserved executor responsiveness and increased total elapsed time in this run. It does not make parsing itself faster. Typed error tests and stale-response/version tests cover separate correctness requirements. The heartbeat is an executor probe rather than a native IPC round-trip measurement.

# Code-mode keystroke latency — 2026-10-30

Follow-up to the open boundary in [2026-10-21](2026-10-21.md): the 10,000-line
source sample exceeded the 16 ms input budget at p95. This record covers what was
changed in the code view, what the change measures, and how much of the remaining
latency belongs to the browser rather than to Taleno.

## What changed

`src/components/CodeView/CodeView.tsx` no longer does avoidable whole-document
work on each keystroke:

1. **The textarea is no longer a controlled value binding.** SolidJS assigned
   `textarea.value` on every document change, including the identical string the
   textarea had just produced while typing. The value is now pushed only when the
   DOM actually holds something else (reload, undo, tab switch, plugin insert).
2. **The gutter window is compared before it wakes the DOM.** `sameGutterWindow`
   is used as the memo's equality function: typing inside the visible document
   usually leaves `start`, `offsetTop`, `totalHeight` and every mounted line
   unchanged, and an equal window must not rewrite ~50 inline styles per key.
3. **Document analysis is cheaper.** Line count, longest line and non-ASCII
   detection now split once and read `line.length`/`indexOf("\t")` instead of
   visiting every UTF-16 code unit, and the split array is reused by the
   measurement path.

## Method

- Builds: production Vite build, installed dependency lock, Node 24.15.0,
  Chrome 156.0.8078.76, Windows 10 host, mocked IPC.
- `node scripts/measure-codeview-performance.mjs BASE_URL OUTPUT_JSON 4`: the app
  in code mode with 10,000 seeded lines and 60 real key inputs at 20 ms spacing,
  alternating with a bare `<textarea>` that receives the same text, font, padding,
  line height and wrap settings and runs no application code. The floor isolates
  browser textarea layout from application work.
- Baseline and optimized builds were measured in adjacent windows on the same
  host; each figure below is the median of four runs (raw per-run values are in
  the linked JSON).
- Samples start at `beforeinput` and end after document-level delegated handlers.
  They exclude idle serialization and GPU presentation; animation-frame samples
  additionally include frame scheduling.

| Probe (median of 4 runs) | Before | After | Bare textarea floor |
| --- | ---: | ---: | ---: |
| Source input handler p50 (ms) | 12.1 | 11.1 | 10.3 |
| Source input handler p95 (ms) | 13.5 | 12.2 | 11.1 |
| Source input handler max (ms) | 20.8 | 20.2 | 19.5 |
| App work above the floor, p50 (ms) | 1.9 | 0.8 | — |
| App work above the floor, p95 (ms) | 2.6 | 1.1 | — |
| Next-animation-frame p50 / p95 (ms) | 19.1 / 25.1 | 18.4 / 24.4 | 10.8 / 19.4 |

The change removes roughly 1 ms per keystroke at p50 and 1.3 ms at p95, and
reduces Taleno's own contribution to about 1 ms above a bare textarea at p95. On
this host in this window both builds stay under the 16 ms p95 budget, with the
optimized build at 12.2 ms.

## Limits and what remains

- **Absolute numbers move with host load.** Earlier the same day, on the same
  host, the unmodified baseline measured a p95 of 21.7 ms with
  `scripts/measure-browser.mjs`, and a bare textarea measured p95 values between
  15.8 and 18.9 ms in the same windows. The 20.7 ms figure in the
  2026-10-21 record was taken under a different load and Chrome build. Treat a
  single run as a sample, not a verdict, and compare builds measured back to back.
- **Browser textarea layout is the remaining floor.** The bare textarea spends
  ~10 ms at p50 on this document, and its cost scales with line count because
  the whole text is laid out per edit. Application-side changes cannot remove
  that; only a virtualized editor (for example CodeMirror 6) renders just the
  visible lines and would change the input path substantially. That swap is
  recorded in the follow-up section below.
- **Animation-frame p95 stays above 16 ms for both builds**, including the bare
  textarea, so this record claims no universal 60 FPS. Those samples include
  frame scheduling.
- Browser and mocked IPC only: no native Tauri process cold start, no mobile
  hardware, no GPU presentation measurement. Writing mode was not re-measured in
  this round.

## Follow-up: CodeMirror 6 code editor (same day)

The limits above name browser textarea layout as the remaining floor and a
virtualized editor as the only way past it. This section records that swap.

### What changed

`src/components/CodeView/CodeView.tsx` now mounts a CodeMirror 6 `EditorView`
(`@codemirror/state`, `@codemirror/view`, `@codemirror/commands`, MIT) instead of
a `<textarea>`:

1. **Only the visible lines are laid out.** A keystroke no longer lays out the
   whole document.
2. **The custom gutter is gone.** The offscreen measurement mirror,
   `computeGutterWindow`, `analyzeDocumentText`, `sameGutterWindow` and the
   mirrored per-line blocks are deleted; CodeMirror's line-number gutter keeps
   every number on the first visual row of its logical line, wrapped or not.
3. **Undo, selection and scroll are per document** through a bounded map of
   `EditorState` (24 sessions), replacing the module-level snapshot history.
   A reload or another view's edit replaces the document with a fresh state, so
   history restarts exactly where the snapshot history used to reset.
4. **The bridges are unchanged.** Formatting actions, find/replace reveal,
   heading navigation and plugin insertion dispatch editor transactions through
   the same `registerCode*` hooks.

### Method

- Builds: production Vite build of `3c4554e` ("before", textarea) and of this
  branch ("after", CodeMirror); same installed dependency lock, Node 24.15.0,
  Chrome 156.0.8078.76, Windows 10 host, mocked IPC. Both builds were served
  side by side and measured alternating before/after/before/after in one
  session, four runs per measurement, eight runs per build.
- `node scripts/measure-codeview-performance.mjs BASE_URL OUTPUT_JSON 4` with the
  same 10,000 seeded lines, 60 real key inputs at 20 ms spacing and the same
  bare-textarea floor page.
- The script now detects which editor the build ships and ends each sample where
  the application has been notified of the edit: after the input listener for a
  textarea, after CodeMirror's transaction (in a probe `MutationObserver`
  registered behind CodeMirror's own) for the editor. Both figures therefore
  cover "edit applied and application notified"; CodeMirror's DOM update and the
  textarea's layout are what the frame samples add. Before this change the
  textarea's layout was already inside its handler sample.

### Results

| Probe (median of 8 runs) | Textarea (before) | CodeMirror (after) | Bare textarea floor |
| --- | ---: | ---: | ---: |
| Source input handler p50 (ms) | 11.4 | 1.5 | 10.3 |
| Source input handler p95 (ms) | 12.7 | 1.9 | 11.3 |
| Source input handler, worst run max (ms) | 25.6 | 5.4 | — |
| Next-animation-frame p50 / p95 (ms) | 18.4 / 25.0 | 2.8 / 16.2 | 11.9 / 19.7 |

On this host the 10,000-line handler p95 falls from 12.7 ms to 1.9 ms, about
6.7×, and the worst single sample in any run drops from 25.6 ms to 5.4 ms. The
16 ms budget now holds with a wide margin, and the handler no longer touches the
document's layout. Frame p95 for CodeMirror sits at one 60 Hz vsync (~16 ms)
rather than the ~25 ms of dropped frames before; it is scheduling, not editor
work.

The textarea floor in the same windows (10.3 ms p50 / 11.3 ms p95) is unchanged,
which is the point: the editor does not reproduce that cost at all.

### Bundle

| Chunk | Before | After |
| --- | ---: | ---: |
| CodeView (lazy), raw / gzip (kB) | 11.36 / 4.73 | 277.51 / 90.32 |
| Shared keycode module pulled out of the entry (kB) | — | 1.49 / 0.82 |
| Initial entry, raw / gzip (kB) | 305.14 / 83.08 | 304.58 / 82.94 |
| Stylesheet, raw / gzip (kB) | 52.36 / 9.94 | 51.84 / 9.89 |

The editor costs ~268 kB raw / ~86 kB gzip, all of it in the lazily loaded code
view: CodeMirror is not requested until code mode is opened. The initial entry
changes by under 1 kB (a 1.49 kB module shared with the writing editor is now a
separate request instead of being inlined), and no Tauri permission, capability
or IPC command changed.

### Tests and behaviour

- Unit tests: `src/components/CodeView/*.test.tsx` rewritten around the editor
  (13 tests) — store binding, external replacement, per-document undo and
  selection, formatting bridge, table insertion, match reveal, heading
  navigation, line numbering, a mounted-line bound for 10,000 lines, and
  session eviction.
- End-to-end: the three `e2e/codeview-gutter.spec.ts` journeys now assert that
  every rendered line number sits exactly on a rendered line — including
  soft-wrapped ASCII and CJK lines, empty lines, deep scrolling and incremental
  edits — and the two code-mode assertions in `document-integrity` and
  `rendering-acceptance` read the editor instead of a textarea.
- `pnpm lint`, `pnpm test` (203 tests), `pnpm test:e2e` (12 tests) and
  `pnpm build` pass on this host.
- IME: composition is handled by CodeMirror's contenteditable. CJK insertion,
  Tab indentation, click-to-focus below the last line and Ctrl+Z/Ctrl+Y were
  exercised in the production build in Chrome. No iOS or Android device was
  used, so mobile IME remains device verification work.

### Decision

Adopt CodeMirror. It clears the 16 ms target by an order of magnitude, removes
the whole-document layout cost the previous record identified as a floor, and
keeps the Markdown-only data model. The cost is a ~86 kB gzip lazy chunk and a
new dependency family to keep updated; the mobile IME path needs a device pass.
